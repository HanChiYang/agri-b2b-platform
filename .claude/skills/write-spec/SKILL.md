# 寫功能規格

規格是寫測試和程式的依據，使用者確認之前，hook 會擋下 `src/`、`tests/` 的修改。這個 skill 的目標是：使用者確認規格的時候，該決定的事都已經問過，不要等到審查或實作時才發現。

階段 2 的經驗是：使用者很難從一份長文件裡發現「這裡漏了什麼」，但回答一個明確的問題只要幾秒。所以重點有兩個：

1. 自己把規則想完整。欄位的預設值、唯一怎麼比較、格式、出錯時回什麼，這些是寫規格的人該想到的，不該靠使用者挑出來
2. 只有使用者能決定的事，整理成明確的選擇題來問

## 開始之前

- 照 CLAUDE.md 的 Git 流程，在 `feature/<簡短描述>` branch 上做。規格檔是 `docs/specs/<branch 名稱去掉 feature/>.md`
- 規格的狀態（草稿 → 已確認 → 已完成）和 hook 的行為，見 CLAUDE.md 和 `docs/specs/README.md`

## 步驟

### 1. 讀資料

- `docs/plan.md`：這個階段的項目和完成標準、第 6 節資料模型、第 9 節需求確認紀錄，以及這個階段底下「寫規格時要考慮」的項目（之前審查時延後處理的事）
- `docs/adr/README.md` 裡和這次有關的 ADR
- `docs/specs/README.md` 裡已完成的規格：這次會不會改變它們的行為
- 現有的程式，例如資料表的實體和設定。規格要建立在現有的結構上，要改的話寫清楚

### 2. 寫草稿

從 `docs/specs/_template.md` 複製，加進 `docs/specs/README.md` 的清單，狀態「草稿」。寫的時候用下面的「檢查清單」逐項想過。

### 3. 問使用者

把「待確認」的問題用選擇題問使用者（見「怎麼問」），同時寫在規格的「待確認」段落，使用者之後看規格時也看得到。

### 4. 寫回結論，請使用者確認

- 使用者回答後，把結論寫進規格對應的段落，從「待確認」移除。理由寫在決定旁邊，之後的人才知道為什麼這樣決定
- 決定和 plan 不同時，一併更新 plan，並在規格寫「和 plan 不同的地方」；重要的決定另外寫 ADR
- 全部寫好後，請使用者看過整份規格。使用者同意後，把狀態改成「已確認」（會跳出確認視窗）。在這之前不寫測試和程式

### 5. 確認之後還要修改時

確認之後的每次修改都會跳出確認視窗，所以把要改的地方整理好，一次改完。會改變已完成規格的行為時，寫在「影響到的既有規格」。

## 檢查清單

### 從 plan、ADR 沿用的決定

plan 是專案剛開始時寫的，那時資訊比較少，很多細節要到寫規格時才看得到。沿用 plan 或 ADR 的決定時，挑出「之後很難改」的，明確問使用者要沿用還是要改：

- 資料的型別，例如金額有沒有小數
- 必填或選填、能不能重複
- 要不要存某個資料，範圍裡的某個功能還要不要做

階段 2 的例子：plan 寫金額用 `numeric(12,2)`，草稿直接沿用，到審查時才決定只用整數（ADR-0016）；plan 裡的網站內容資料表，後來決定不做、寫死在前端（ADR-0015）。如果寫草稿時就問「金額會有小數嗎？」「網站內容要在後台編輯嗎？」，一開始就能決定。

之後容易改的，例如顯示的文字、排序方式，不用問，直接決定寫進規格。

### 每個欄位

- 必填或選填。選填的話，空字串要存成空值還是擋下來
- 預設值：布林、狀態、次數這類欄位，新增時沒有指定的話是什麼
- 唯一：怎麼比較（大小寫、前後的空白），沒填的算不算重複，由 API 還是資料庫負責轉換
- 格式、長度、範圍：例如統一編號是 8 位數字、金額不可小於 0
- enum：允許哪些值；沒有指定時會怎樣（C# 的 enum 沒有設定時是 0）

### API

- 誰可以呼叫：沒登入、角色不對時回什麼
- 請求的欄位不合規定時回什麼（專案統一用 ProblemDetails）
- 找不到資料、目前的狀態不允許這個操作時回什麼
- 同時有好幾個請求時會不會出問題，例如訂單編號會不會重複

### 寫行為，不寫實作

- 規格寫「要什麼行為」，不寫「程式怎麼判斷」。階段 2 的草稿寫「Development 和 Testing 環境自動套用 migration」，等於規定程式要判斷環境名稱；後來改成「由設定決定，開發和測試時打開」
- 測試怎麼寫（例如測試資料怎麼產生）不寫進規格

## 驗收條件

- 寫真正重要的行為：資料正確、權限、使用者看得到的結果、出錯時的回應。實作細節不寫成驗收條件：每一條都要寫測試、之後一直維護，寫得太細，審查也能一直挑下去（ADR-0017）
- 每一條都要能寫成整合測試。「預期結果」要具體到測試能直接檢查，例如回傳哪個狀態碼、資料庫存了什麼
- 同一條規則的正反兩面放在同一條，例如「統一編號不能重複；沒填的可以有好幾家」
- 編號從 AC-1 開始

## 怎麼問

- 用 AskUserQuestion 問：一次最多 4 題、每題 2–4 個選項。建議的選項放第一個，標「（建議）」；每個選項的說明寫理由，以及選了之後會怎樣。題目多時分幾次問
- 只問使用者才能決定的事：業務規則、要不要做、要不要沿用 plan 的決定。技術上的選擇自己決定，理由寫在規格裡，使用者確認規格時看得到；只有影響很大、或兩種做法各有明顯代價的才問
- 規格的「待確認」段落寫同樣的題目，每題附上建議和理由

## 範例

`docs/specs/phase-2-data-model.md` 是一份完成的規格，可以參考：

- 「共通規則」：所有資料表共用的規則集中寫一次
- 欄位表格下面用一段話說明為什麼這樣決定，例如統一編號為什麼選填、商品的四個欄位為什麼必填
- 「和 plan 第 6 節不同的地方」：規格和 plan 不同時怎麼記錄

這份規格寫完草稿後，又補了下面這些，都是上面的檢查清單想事先抓到的：

| 後來補的 | 檢查清單的哪一項 |
|---|---|
| 金額只用整數、網站內容不做 | 從 plan、ADR 沿用的決定 |
| 帳號、分類、商品的預設值（AC-11） | 每個欄位：預設值 |
| 帳號不分大小寫、前後不能有空白（AC-14） | 每個欄位：唯一怎麼比較 |
| 統一編號必須是 8 位數字（AC-15） | 每個欄位：格式 |
| 角色和訂單狀態只能存定義的值（AC-13） | 每個欄位：enum |
| migration 改用設定控制 | 寫行為，不寫實作 |

AC-12（時間截到微秒）則是寫得太細的例子：它是實作細節，不影響使用者看到的結果。
