# ADR-0018：主鍵用 UUIDv7

- 狀態：已接受
- 日期：2026-10-25

## 背景

階段 2 的主鍵是整數，由資料庫依序產生。從階段 3 開始，id 會出現在 API 的網址（例如 `/api/orders/{id}`）和 JWT 裡，整數 id 有幾個問題：

- 連續的數字透露業務量：經銷商從自己訂單的 id 推算得出公司的訂單量，從自己帳號的 id 看得出有幾家經銷商
- 容易猜：把網址的數字加 1 就能試別人的資料。經銷商只能看自己的訂單，這個權限檢查還是一定要做，但 id 猜不到是多一層保護
- 要存檔之後才知道 id

目前還沒部署，沒有要保留的資料，現在改的成本最低；API 開始用 id 之後再改，每個階段都要跟著改。

## 決策

- 所有資料表的主鍵改成 `uuid`（C# 用 `Guid`），外鍵跟著改
- 用 UUIDv7：前面是產生的時間，新的 id 都加在索引的最後面
- 新增時由程式產生，資料庫欄位不設 DEFAULT
- 還沒部署，所以直接重新產生第一個 migration，不另外寫轉換用的 migration

細節見[規格](../specs/uuid-primary-keys.md)。

## 考慮過的其他方案

- 維持整數：最簡單、佔的空間最小，人工查資料時也好唸；但有上面的問題
- 內部用整數主鍵，另外加一個對外用的 UUID 欄位：資料庫內部用整數 join 比較快，但每張表有兩種識別碼，API 每次都要轉換，容易用錯。這個系統的資料量用不到這種最佳化
- UUIDv4（完全隨機）：從 id 看不出新增時間，但新增時會插在索引的任意位置，索引變得零散。這個系統的新增時間不是機密，`created_at` 也會顯示給使用者
- 由資料庫產生（PostgreSQL 18 的 `uuidv7()`）：存檔之後才知道 id，也不符合「資料庫欄位不設 DEFAULT」的規則

## 影響

- 每個 id 佔 16 bytes，整數是 4 bytes；這個系統的資料量不受影響
- id 很長，不適合人工查詢或電話溝通，這時用訂單編號、帳號、統一編號
- 從 id 看得出新增的時間（精確到毫秒）
- 同一毫秒內新增的資料，id 的大小不代表先後順序，需要排序時用 `created_at`
- 已經套用過舊 migration 的本機資料庫要刪掉重建
