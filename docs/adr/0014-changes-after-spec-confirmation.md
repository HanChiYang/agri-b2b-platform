# ADR-0014：規格確認之後的修改流程

- 狀態：已接受
- 日期：2026-10-24

## 背景

[ADR-0013](0013-hook-enforced-spec-confirmation.md) 確保規格經過使用者確認，才開始寫測試和程式。但規格確認之後，還有幾種情況沒有規則：

- **實作中修改規格**：規格和程式在同一個 branch 裡。實作卡住時，如果規格被改成配合程式，spec-reviewer 對照的就是改過的規格，會判斷「符合規格」；最後的 diff 裡規格整份都是新增，看不出確認之後改過
- **「待確認」的結論只留在對話裡**：使用者在對話裡回答了問題，規格卻沒有更新就被改成「已確認」，審查者看不到這些結論
- **後面的階段改變前面規格的行為**：例如在已經有的資料表加欄位，前面規格的測試就會失敗、必須修改。但 `CLAUDE.md` 規定不可以為了讓測試通過而修改測試，spec-reviewer 也會把它列為問題
- **修 bug**：`CLAUDE.md` 只規定了 branch 名稱，沒有規定流程

## 決策

- `.claude/hooks/require-confirmed-spec.mjs` 加上兩項檢查：
  - 規格已經是「已確認」或「已完成」時，任何修改都跳出確認視窗，由使用者決定
  - 「待確認」段落還有項目時，不能把狀態改成「已確認」
- 規格範本加上「影響到的既有規格」：列出這次會改變哪些已完成規格的哪幾條驗收條件、要改哪些測試，使用者確認規格時一起確認
  - 實作時照這裡修改舊規格的內容和測試，讓每份規格都描述目前的行為
  - spec-reviewer 檢查：列出的修改都做了，沒列出的舊規格和測試沒有被改，改過的測試驗證的是新的行為，而不是單純放寬
- 修 bug：先寫一個重現 bug 的測試並確認失敗，再修到通過。bug 是規格沒寫到的情況時，先問使用者，同意後在那份規格補上驗收條件。不用另外寫新規格

## 考慮過的其他方案

- 規格確認時另外 commit 一次，審查時比對確認之後的修改：會讓 commit 太細碎；跳出確認視窗就能做到同樣的把關
- 舊規格保持原樣，只在新規格寫差異：要拼湊好幾份規格才知道目前的行為，審查時對照舊規格也會誤判
- 修 bug 也寫一份新規格：大部分的 bug 只是程式沒做到規格寫的事，寫新規格太重

## 影響

- 規格確認之後的每次修改都會跳出確認視窗，包含收尾時改成「已完成」那次
- 已完成的規格會被後面的階段修改，描述的是目前的行為；當時的版本要看 git 歷史
- hook 依「待確認」段落的格式判斷（`## 待確認` 底下第一層的項目，只有「-」或「- 無」不算），修改範本時要一起檢查 hook
- 仍然擋不住用 shell 指令修改規格，這部分靠 `CLAUDE.md` 的規則
