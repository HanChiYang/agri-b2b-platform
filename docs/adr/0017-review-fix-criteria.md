# ADR-0017：審查結果只修重要的問題

- 狀態：已接受
- 日期：2026-10-25

## 背景

[ADR-0012](0012-fresh-context-review.md) 讓沒有上下文的 agent 在完成前審查。階段 2 審查了兩輪，每一輪都找到十幾項，修完再審查又找到新的。後來的項目大多是現在不會發生的假設情況，例如目前沒有程式這樣寫、正式環境的設定。

被要求找問題的審查者一定找得到東西，「審查到沒有問題」不會發生。沒有標準的話，這個流程停不下來。

## 決策

- 審查結果符合下面任一條，才建議修：
  - 規格的驗收條件沒做到，或那條完全沒有測試
  - 在現在或下一個階段真的會發生，而且會存錯資料、有安全漏洞，或讓建置、CI、本機開發跑不起來
- 其他的一律建議不修，每項只寫一行理由。和之後階段有關的，用一行記在 `docs/plan.md` 對應的階段，寫那個階段的規格時再考慮
- 修完只重新跑測試，不再整份審查。修改本身很大時，才再審查一次，而且只審查這次修改的部分
- 驗收條件寫真正重要的行為，例如資料正確、權限、使用者看得到的結果，不寫實作細節。寫得太細，審查就能一直挑下去
- 最後還是由使用者決定修哪些

## 考慮過的其他方案

- 每一項都修，修到審查沒有問題：不會結束，每次修改又會帶來新的審查項目
- 不再審查：會漏掉真正的問題，例如階段 2 第二輪找到的 docker-compose 健康檢查，會讓新 clone 的人第一次啟動就失敗
- 把標準交給審查者，讓它只回報符合的項目：審查者不知道之後的階段會怎麼用這些程式，判斷不準。由審查者全部列出、再依標準整理，使用者也看得到被判斷為不修的項目

## 影響

- 每個階段審查一輪就能收尾
- 不修的項目之後可能真的發生，所以和之後階段有關的要記在 plan，寫那個階段的規格時一起看
