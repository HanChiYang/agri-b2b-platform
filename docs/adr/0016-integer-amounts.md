# ADR-0016：金額只用整數

- 狀態：已接受
- 日期：2026-10-25

## 背景

[ADR-0002](0002-postgresql-and-ef-core.md) 決定金額存 `numeric`，階段 2 的規格原本寫成 `numeric(12,2)`，C# 用 `decimal`。

審查時發現，`numeric(12,2)` 遇到超過 2 位小數的值，PostgreSQL 會先四捨五入再檢查限制：

- -0.004 會變成 0.00，通過「不可小於 0」的檢查
- 450.005 會存成 450.01，C# 物件上卻還是 450.005，兩邊不一致

經銷商的價格、訂單金額都是新台幣整數元，用不到小數。

## 決策

- 金額只用整數（新台幣元），資料庫存 `bigint`，C# 用 `long`
- 取代 ADR-0002 中「金額存 `numeric`」這一點，ADR-0002 的其他決策不變

## 考慮過的其他方案

- `numeric(12,2)` + `decimal`，由 API 檢查最多 2 位小數：每個寫入金額的地方都要記得檢查，直接用 SQL 寫入時資料庫還是會悄悄四捨五入
- `numeric` + `decimal`，再加「必須是整數」的檢查條件：C# 的型別還是能放小數，只是存檔時才失敗
- `int`：單價乘數量算小計時，超過約 21 億就會溢位，C# 預設不會報錯，只會算出錯的數字。`long` 的上限遠大於實際金額

## 影響

- C# 的型別本身就沒有小數，算金額時不用擔心四捨五入
- API 收到有小數的金額時，JSON 轉換就會失敗，自動回 400
- 前端的 JavaScript 數字在 2^53 以內都是精確的，遠大於實際金額
- 之後要支援小數（例如外幣、折扣到角）時，`bigint` 轉成 `numeric` 不會遺失資料，C# 改回 `decimal`，再寫一份新的 ADR
