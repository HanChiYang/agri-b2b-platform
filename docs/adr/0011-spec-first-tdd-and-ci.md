# ADR-0011：先寫規格和測試再實作，並由 CI 把關

- 狀態：已接受
- 日期：2026-10-24

## 背景

這個專案的程式主要由 AI 程式助理（Claude Code）撰寫，使用者負責確認需求和審查。要讓 AI 的產出穩定可靠，需要兩種機制互相配合：

- 事前引導：動手前講清楚要做什麼，例如規格
- 事後檢查：做完後自動檢查，讓錯誤能當下被發現並修正，例如編譯器、測試、CI

原本只有 `CLAUDE.md` 的文字規則和少量測試。文字規則只是建議，工作一多或對話被壓縮後就可能被忽略；AI 自己寫的測試，也可能和程式犯同樣的理解錯誤。

## 決策

- 每個階段或功能開工前，先寫規格（`docs/specs/`），列出編號的驗收條件；使用者確認後才開始寫測試
- 每條驗收條件至少對應一個整合測試。先寫測試、確認失敗，再實作到通過；實作時不能為了讓測試通過而修改或刪除測試
- 建置時警告一律視為錯誤，並啟用 .NET 建議的程式碼分析規則（`Directory.Build.props`）；格式規則寫在 `.editorconfig`
- GitHub Actions 在每個 PR 檢查格式、建置和測試；`main` 的保護規則要求這項檢查通過才能合併

## 考慮過的其他方案

- GitHub Spec Kit 等規格驅動開發工具：流程完整，但和現有的 `docs/plan.md`、ADR 大量重疊，還會產生許多檔案和指令；一人開發的專案，用一份規格檔加上測試就夠了
- 每次改檔就自動跑測試的 hook：每次測試都要啟動 PostgreSQL 容器，太慢；而且先寫測試的階段，測試本來就該失敗，會擋住流程。先靠 CI 把關，如果發現測試常被漏跑再加
- 只在 CI 把警告視為錯誤：本機建置就擋下來，AI 當下就看得到錯誤並修正，不用等推上 GitHub

## 影響

- 每個功能多一份規格文件，開工前要等使用者確認
- 測試可以和驗收條件逐條對照，審查 PR 時比較容易確認功能做對了
- 套件出現已知漏洞時，建置也會失敗，要升級套件才能繼續
- 關掉任何檢查規則都要寫明原因；目前只有測試專案關掉 CA1707、CA1711 兩條命名規則（見 `.editorconfig`）
- 這套流程從階段 2 開始試行，順利的話再寫成 Claude Code 的 skill
