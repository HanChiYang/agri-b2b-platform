# ADR-0013：用 hook 確保規格經過使用者確認，才開始寫測試和程式

- 狀態：已接受
- 日期：2026-10-24

## 背景

[ADR-0011](0011-spec-first-tdd-and-ci.md) 規定使用者確認規格之前，不寫測試和程式。這條規則只寫在 `CLAUDE.md`，而 ADR-0011 也提到，文字規則在工作一多或對話被壓縮後可能被忽略。規格還沒確認就寫了測試和程式，規格一改，測試和程式都要跟著重寫。

這條規則可以從檔案判斷：規格檔放在固定的位置（`docs/specs/<branch 名稱去掉 feature/>.md`），開頭寫了狀態（`- 狀態：草稿`）。

## 決策

- 新增 PreToolUse hook `.claude/hooks/require-confirmed-spec.mjs`：
  - 在 `feature/` branch 上用 Edit、Write 修改 `src/`、`tests/` 時，對應的規格不存在，或狀態不是「已確認」「已完成」，就擋下來
  - 把規格的狀態改成「已確認」或「已完成」時，跳出確認視窗，由使用者決定是否允許。規格是不是確認了，由使用者按下允許決定，Claude 不能自己改
- `fix/` branch 不檢查：修 bug 不一定會寫規格
- 只擋 `src/`、`tests/`：文件、CI、Claude Code 設定的修改不受影響

## 考慮過的其他方案

- 只靠 `CLAUDE.md` 的文字規則：原本的做法，問題見背景
- 在 CI 檢查：推上 GitHub 時程式已經寫完了，太晚
- 由使用者自己修改規格的狀態：一樣能確保經過使用者確認，但要自己開檔案改；跳出確認視窗比較省事
- 也檢查 shell 指令（例如 `sed`、`Set-Content`）寫入的檔案：要可靠判斷一個指令會不會寫檔很難，容易誤擋

## 影響

- 寫規格的階段，Claude 只能改文件；規格確認後才能動 `src/`、`tests/`
- 每份規格多一次確認視窗
- 擋不住用 shell 指令寫檔，這部分仍然靠 `CLAUDE.md` 的規則
- 規格開頭狀態的寫法變成 hook 依賴的格式，修改 `docs/specs/_template.md` 時要一起檢查 hook
