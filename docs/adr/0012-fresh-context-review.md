# ADR-0012：完成前交給沒有上下文的 agent 審查

- 狀態：已接受
- 日期：2026-10-24

## 背景

[ADR-0011](0011-spec-first-tdd-and-ci.md) 的編譯器、測試和 CI，只能確認程式和測試彼此一致，發現不了「測試和程式一起理解錯規格」的情況。寫程式的 AI 也容易認為自己剛寫的程式是對的。

Claude Code 官方的 best practices 建議：認定工作完成之前，讓一個 subagent 在全新的上下文裡審查 diff。審查者只看得到變更和審查標準，看不到寫程式時的推理過程，比較能用自己的角度判斷。

## 決策

- 每個階段測試全部通過後、commit 前，做兩種審查：
  - `spec-reviewer`（`.claude/agents/spec-reviewer.md`）：對照規格，檢查每條驗收條件是否都有測試、實作是否符合規格、有沒有超出範圍、測試有沒有被放水
  - 內建的 `/code-review`：找 bug
- 審查者只拿到規格檔的路徑，看不到開發時的對話，也不附上寫程式的人的說明
- `spec-reviewer` 固定使用 Opus：不比寫程式的模型弱；寫死在設定檔，主對話換成較小的模型時，審查品質不會跟著下降
- 審查者只回報影響正確性或不符合規格的問題。結果整理給使用者，由使用者決定修哪些

## 考慮過的其他方案

- 只用 `/code-review`：能找 bug，但不知道規格，無法檢查驗收條件是否都做到
- 在 GitHub Actions 上自動用 AI 審查每個 PR：要設定 API 金鑰、依用量付費；一人開發的專案，在本機審查就夠了
- 審查者用 Fable：能力更強，但依方案可能要另外付費；每個階段的變更不大，Opus 就夠。重要的階段可以改設定檔的一行換成 Fable
- 審查者跟著主對話的模型（`inherit`）：主對話換成較小的模型時，審查品質會跟著下降

## 影響

- 每個階段多花一些用量和時間
- 審查者和寫程式的是同一類模型，有些盲點會相同；CI、測試和使用者審查 PR 仍然必要
- AI 審查的結果不一定每次相同；被要求找問題時，也可能挑出不重要的問題，所以由使用者判斷要不要修
